# 超声波间歇无读数排查

2026-11-03，在 30 颗灯带更新后，用户报告 Indicator 水箱距离无读数。主控读取确认：超声波功能已启用，土壤及 SEN54 更新正常，原水箱 35 / 61 / 80 mm 标定保留，但距离无效。固定平板测试未恢复；用户断电重插后报告短暂恢复，随后再次确认无读数。没有据此认定模块损坏或问题已修复。

为区分测距超时、超界和采样过期，在原测距路径增加只读诊断：`water_tank.echo_us`、`signal_high`、`sample_age_ms`、`error`。仍使用 GPIO8、12 µs 触发和 25 ms 等待上限；未更改标定、有效距离范围或无效水位禁泵保护。没有自动重试浇水，也没有用旧距离代替失效采样。

- 主控构建通过，498 项控制器、13,563 项灯效检查及其余现有核心测试通过；新增超声波诊断分类和过期测试通过。
- 仅更新 XIAO 应用区，保留 NVS；原应用、分区与 MAC 在刷写前核对，备份留在本地。
- 诊断版应用镜像：2,397,632 字节，SHA-256 `85296ad6447c3eb718151ecfc6640f1b9909fdd5d3b776f5556587915edf85b4`。

诊断版刷入并校验通过。16:40（北京时间）三次读取均为 `signal_high_after_timeout`、`echo_us:0`、`signal_high:true`，采样年龄小于 1 秒；土壤与温湿度有效，标定保留，水泵保持关闭。这表示等待脉冲超时后引脚仍为高，尚不足以单独区分模块无回波、接线、供电或引脚电气问题。

用户测得模块端 VCC 为 3.3V、SIG 为 2.7V。静态供电处于官方 3.2–5.2V 范围，但万用表不能确认触发／回波波形或排除瞬态掉压；SIG 读数也不能单独证明短路。随后一次约一分钟观察，42 次有效 HTTP 响应均无有效距离，另有 2 次 HTTP 超时；恢复响应后仍报告回波超时且 SIG 高。

正在排除线束、接头及模块／主控信号问题，尚未完成恢复验收。相关字段见[设备协议](../device-protocol.md)，操作说明见[排障手册](../handbook/troubleshooting.md#超声波无回波--浇水不可用)。

## 更换线束、模块与端口对照

用户换用另一块同型号 Ranger v2.0 和另一条线后，GPIO8 仍报告超时且 SIG 高。随后确认将黄线移到空闲 SERVO4/J14 的 D8/GPIO7，打印机 TTL 已断开，打印走 BLE；供电仍为独立 3.3V、共地。

增加可选编译项 `ROBO_ULTRASONIC_GPIO`（默认 8，只允许 7 或 8），HTTP 增加 `signal_gpio` 便于核对实际固件。编译检查确认：默认 GPIO8、GPIO8 配 UART 打印、GPIO7 配 BLE 打印可用；GPIO7 与 UART 打印冲突、GPIO8 与旧 Air ADC 冲突、非法引脚均拒绝。

D8 对照应用 SHA-256 为 `4f8f9ad3ef6f6cc13c448099b0ca2670f753748d730de51688f961fb83e906fb`，2,397,680 字节，已刷写校验。16:48–16:49 四次读取均为 `signal_gpio:7`、`echo_timeout`、`signal_high:false`，尚未取得距离。这个变化不足以证明 GPIO8 损坏。

原 Arduino `pulseIn` 会先等当前高电平结束，再等下一次高电平；若调用时本次回波已开始，存在漏测可能。为排除此时序问题，准备在触发下降沿之后、释放 SIG 切回输入之前，预先启用 GPIO 边沿记录。它保留 25ms 上限；只有完整的升／降沿才计算脉宽，过短脉冲、缺沿、超时、采集溢出仍拒绝。边沿解码与既有控制／水箱保护测试通过，实体结果待后续记录。

边沿版应用已刷写校验，SHA-256 `9aa350d57d47a587d6aeb9876422cf3ee57b09c546312395054aec4ae49b593b`，2,400,256 字节。16:51 四次读取均为 GPIO7、`edge_count:0`、`capture_overflow:false`、`echo_timeout`、`signal_high:false`，土壤与温湿度有效。改变接收方式尚未恢复测距，不能把此前关于漏测快速回波的可能性写成已证实根因。下一步对比模块 SIG 与主控 D8 两端电压。

## 触发电平自检

用户确认模块 SIG 与主控 D8 对各自 GND 均测得约 0.4V。万用表直流读数不能代替短脉冲波形，因此增加触发期间的 GPIO 读回：低电平等待 2 µs 后、高电平等待 12 µs 后各检查一次，并记录全轮中断次数。若读回与要求不符，本次距离仍保持无效，不放行水泵。

自检版应用已刷写校验，SHA-256 `e86c1f8eb66998836e50eddc871af5ee5f2e783ee5b6da4dee597b01c8455e45`，2,400,640 字节；仅改应用区，保留配对和标定。16:54–16:55 读取显示 `trigger_low_ok:true`、`trigger_high_ok:false`、`irq_edges:0`、`edge_count:0`，错误为 `trigger_level_mismatch`，泵保持关闭。这比无回波更进一步定位到触发高电平读回失败，但还不足以区分外部负载、接线、主控端口或 GPIO 配置问题。

已请求用户断电后只从 D8 拔下超声波黄线、重新上电，等待空载读回对照；此项尚未验收，不能将本次诊断写成修复完成。

用户随后确认已从 D8 拔下黄线并重新上电。16:58 三次读取仍为 `trigger_low_ok:true`、`trigger_high_ok:false`、`irq_edges:0`；传感器已不接在这个信号针上，故不能继续将该读回失败简单归因于超声波模块。

## 独立 GPIO 空载对照

新增 [`firmware/xiao-gpio-diagnostics`](../../firmware/xiao-gpio-diagnostics/README.md)，在不运行测距、网络、蓝牙、灯效业务的情况下测试引脚。只接受指定 D8 / D9 的串口命令，各用 Arduino 和 ESP-IDF 两种方式做一次低／高／低读回，记录输出寄存器、使能、复用与输入状态；不自动循环，不写 NVS，泵和电机保持关闭。

| 空载端口 | 要求低时的输入 | 要求高时的输入 | 输出寄存器 / 使能 | 两种方式结果 |
| --- | --- | --- | --- | --- |
| D8 / GPIO7 | 0 | 0（异常） | 分别 0、1，输出使能为 1 | 一致 |
| D9 / GPIO8 | 1（异常） | 1 | 分别 0、1，输出使能为 1 | 一致 |

两路的 `mux=0x00001a00`、`route=0x00000100`，驱动 API 返回成功。D8 已由用户确认断开，D9 自超声波移至 D8 后空闲。独立程序仍复现相反方向的电平异常，使怀疑重点转向 XIAO 或底板的硬件信号路径；尚不能区分芯片引脚、底板保护器件或板上连接问题，需要将可拔插的小主控与底板隔离对照。此时仍未恢复水位读数，不应改标定或放松禁泵保护。

两轮独立测试均在核验 MAC、原应用与分区、备份 NVS 后仅写入应用区，测试结束均已恢复并校验原应用 `e86c1f8e…5e45`。D8 专用诊断镜像 SHA-256 为 `39623d87910c4688f91fd9f7ff97782433e58e285b6b5c9d646863c5b536d4a6`；增加 D9 后的诊断镜像为 `7775515a157b5cc7eb0784d8090df2f5ec26424512a9813030c6b4bd8a7ee0f8`。串口原始结果、恢复日志和备份留在本地 `build/device-backups/xiao-20261103-d8-isolation` 与 `xiao-20261103-d9-isolation`，不包含在公开仓库。

## 用户报告裸板后的复核：隔离状态仍需核实

用户两次确认已将小主控从底板拔下、只有 USB 连接且排针悬空。17:02 网络状态却仍给出 SEN54 有效温湿度和颗粒物数据；禁用 HTTP 代理的直连读取也相同。COM15 串口报告的 IP 仍为 `192.168.88.148`。

因此再次使用不含网络功能的独立诊断，并增加 GPIO4 空载参照及 I²C 空地址应答探测。USB 串口结果：GPIO7 仍无法读回高电平、GPIO8 仍无法读回低电平；GPIO4 在两种驱动方式下均正常读回低／高／低。I²C 的 0x38、0x44 不应答，但 **0x69、0x6a 仍应答**。这与“所有排针悬空”的报告存在矛盾，尚不能把结果当作已经彻底隔离底板的证据，也不能据此确认 XIAO 芯片损坏。

本轮诊断镜像 SHA-256 `441e0b92bb69f40836976f0d93e512474a624dec9d7917365c87eb57d0fceb7b`，282,352 字节。已恢复并校验原应用，NVS 保留，原始日志位于本地 `build/device-backups/xiao-20261103-bare-gpio`。当前 COM15 USB 标识为 `303A:1001`，串号与芯片 MAC 均为 `94:A9:90:CF:82:AC`。下一步要求用户只拔下手里这块 XIAO 的 USB，核对 COM15 是否消失，先建立物理板与测试端口的可靠对应，再决定更换主控或改用其他信号脚。
